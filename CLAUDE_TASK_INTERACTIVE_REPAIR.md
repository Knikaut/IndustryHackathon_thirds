# Задача для Claude Code: интерактивная диагностика и ремонт

Рабочий каталог: `/Users/bauyrzanesekeev/PhpstormProjects/hackAllur`.

Контекст: в проекте уже есть отдельная страница `http://localhost:8000/scenarios` с четырьмя сценариями отказов. Сейчас `ScenarioLab.advance()` всегда проходит диагностику, ремонт и проверку без выбора. Codex отдельно готовит фронтенд под описанный ниже контракт. Твоя зона — **бэкенд и его тесты**; не меняй `frontend/`, не откатывай существующие незакоммиченные правки и не делай коммит без отдельной просьбы пользователя.

## Цель

Пользователь должен выбрать диагноз и способ устранения. Ошибка тратит модельное время и сохраняется в журнале. Проверочный пуск может провалиться; пост остаётся в простое, пока причина реально не устранена. На правильном пути поведение остаётся как сейчас: простой закрывается, состояние узла восстанавливается до 97 %.

## Контракт API с фронтендом

Сохрани существующий `GET /api/scenarios` и старый `POST /api/scenarios/advance` для обратной совместимости. Для новых сценариев добавь:

- `POST /api/scenarios/diagnose` с JSON `{"option_id":"..."}`.
- `POST /api/scenarios/repair` с JSON `{"option_id":"..."}`.
- `POST /api/scenarios/verify` без тела.

Успешный ответ каждой команды — актуальный объект `active` из `GET /api/scenarios`. Неизвестный option ID и неверный этап — HTTP 400 или 409 с понятным `detail`; неизвестный сценарий — 404. Защити переходы общим `engine.lock`.

Каждый элемент `catalog` должен дополнительно содержать:

```json
{
  "public_title": "На посту W3 нарушена геометрия",
  "diagnosis_options": [
    {"id":"sensor", "label":"Ошибка датчика положения", "hint":"Сверить контрольную точку", "minutes":10},
    {"id":"drive", "label":"Неисправность привода", "hint":"Проверить ток и движение", "minutes":10}
  ],
  "repair_options": [
    {"id":"replace-sensor", "label":"Заменить датчик и откалибровать", "hint":"Нужен датчик положения", "minutes":25},
    {"id":"restart-drive", "label":"Перезапустить привод", "hint":"Без замены датчика", "minutes":10}
  ]
}
```

Для каждого из четырёх сценариев — минимум два правдоподобных диагноза и два действия. `public_title` и `symptom` не должны раскрывать правильный ответ; поле `cause` для нового UI можно сохранить ради совместимости, но правильность должна определяться только на сервере. Не добавляй в публичный каталог флаг `correct`.

Объект `active` дополнительно возвращает необязательное поле:

```json
"feedback": {"kind":"success", "text":"Сигнал датчика подтвердил смещение"}
```

`kind` — `success`, `warning` или `error`. Фронтенд также показывает существующие `stage`, `downtime_min` и `log`.

## Поведение

1. Правильный диагноз тратит указанное число рабочих минут и переводит `diagnose → repair`. Ошибочный диагноз тратит время, оставляет `diagnose`, даёт объяснение в `feedback` и запись в `log`; правильный ответ автоматически не раскрывается.
2. Выбранный ремонт тратит свои минуты и переводит `repair → verify`. Пока пост удерживается в простое; запись содержит выбранное действие.
3. `verify` после правильного ремонта закрывает простой и переводит `verify → done`. После неверного ремонта проверка сообщает конкретный наблюдаемый признак неудачи, оставляет пост в простое и переводит `verify → repair`, чтобы выбрать другое действие. Не вызывай `sim.repair()` и не ставь `h=0.97` после неудачной проверки.
4. Между действиями фоновый такт продолжает начислять простой. Длительности вариантов — добавочное модельное время. Вне рабочей смены действуют существующие правила `Engine.tick()`.
5. Один активный наряд за раз. Другие демо-команды на том же посту по-прежнему получают 409. Историю действий и результат проверки держи в текущем in-memory `ScenarioLab`; не обещай постоянное хранение или реальное управление оборудованием.

## Проверки готовности

- Автотесты для верного пути, неверного диагноза, неверного ремонта и повторной проверки, неверного этапа/option ID, блокировки второго наряда и отсутствия самовосстановления поста.
- `PYTHONPATH=. .venv/bin/python -m unittest test_scenarios -v` и `.venv/bin/python check.py` из `backend/` проходят.
- Ручной API-прогон: ошибочный выбор увеличивает `downtime_min`; неудачная проверка не закрывает событие; верный ремонт закрывает его только после успешной проверки.
- В ответе кратко перечисли изменённые файлы, результаты проверок и ограничения. Не меняй фронтенд: он подключается к указанным полям и маршрутам.
